# Mechanical Runtime layer: six crates from precision classification to script-first routing

This change adds the Mechanical Runtime layer to PEARL — the infrastructure that classifies tasks by precision class, routes them to the correct execution backend, enforces pre/post guards with fail-closed semantics, schedules them on cron/interval triggers, and tracks system health for profile degradation. The approach is cleanly layered: `pearl-precision` classifies, `pearl-capabilities` indexes, `pearl-router` decides where to route, `pearl-runtime` executes, `pearl-guard` gates, and `pearl-scheduler` determines when. The dependency chain flows from precision → capabilities → router, with guard and scheduler operating somewhat independently.

Watch for: the `collect_output` stub in pearl-runtime returns empty strings for stdout/stderr, making the structured-output parsing path dead code in real execution (**confirmed**); the router's substring matching on capability IDs can produce false positives with unrelated capabilities (**likely**); the scheduler's misfire `RunAll` with cron expressions iterates minute-by-minute and is capped at 1440 checks (24h), silently dropping missed triggers beyond that window (**confirmed**).

**Verdict**: APPROVED

## High-level view

The Precision Decision Engine is a stateless 4-rule classifier that maps capability declarations to P0/P1/P2/P3. A deterministic capability on a non-mechanical runtime (e.g. ClaudeCode) falls through to P3 rather than P0 — intentional enforcement of Article 1.

The Runtime Adapter wraps the process supervisor with environment filtering, timeout delegation, and a JSON structured-output convention (last line of stdout). However, the critical integration point — actually reading stdout/stderr from the supervised process — is stubbed out with empty strings. The structured output parsing will never fire on real execution until the ProcessSupervisor trait gains a `collect_output` method, and script guards will deny-by-default because they can't read their verdict from stdout.

The Capability Registry loads YAML manifests from disk, classifies each with the precision engine, and provides indexed queries. `load_directory` stops on the first malformed YAML rather than collecting all errors, so a single bad file blocks the entire registry.

The Guard Engine implements Article 7's fail-closed contract with two strategies: inline regex rules (fast path, 6 default patterns matching the reference implementation) and script-based guards (invoked via RuntimeAdapter). The GuardChain composes them with first-deny-wins semantics.

The Scheduler implements cron, interval, one-shot, and manual schedules with a custom cron parser (no external dependency). Profile-aware throttling limits how many tasks fire per poll. The misfire handling has an explicit cap on lookback that could silently lose triggers for extended outages.

The Router searches the capability registry for P0 capabilities, rejects P0 tasks that lack a mechanical path (Article 1), and falls back to agent routing for P1/P2/P3. The matching strategy progresses from exact ID → required_capabilities list → substring match, where the last level introduces ambiguity risk.

<details>
<summary>Issues (5)</summary>

1. **Stdout/stderr collection stub** — `collect_output` in pearl-runtime returns empty strings; the entire structured-output pipeline is inert on real execution. Either expose Child stdio on `SupervisedProcess` or collect output before `wait()` returns.
2. **Router substring matching** — `try_script_route` falls back to `manifest.id.contains(&requirements.task_type)` which can match unrelated capabilities (e.g. task_type "log" matching "catalog"). Require an explicit prefix/namespace convention or remove the substring fallback.
3. **Misfire lookback cap** — `count_missed_triggers` for cron expressions caps iteration at 1440 minutes (24h). Longer outages silently lose missed triggers without reporting. Document the cap or make it configurable via `MisfirePolicy`.
4. **Registry fail-fast on bad YAML** — `load_directory` propagates the first `RegistryError::Parse` immediately, leaving the registry empty even if only one manifest is broken. Consider collecting errors and loading the valid manifests.
5. **Health monitor unbounded Vec** — `HealthMonitor.failures` grows without bound until `prune_stale_failures` is called via `check_profile_transition`. Under sustained failure load without health checks, memory grows linearly with failures.

## Stdout/stderr collection gap in pearl-runtime

The `collect_output` function at the bottom of `pearl-runtime/src/lib.rs` is explicitly documented as returning `(String::new(), String::new())`:

```rust
fn collect_output(proc: &mut SupervisedProcess) -> (String, String) {
    let _ = proc;
    (String::new(), String::new())
}
```

`RuntimeResult.stdout` is always empty in production, so `parse_structured_output("")` always returns `None`. The guard engine's `ScriptGuardEngine` relies on `result.structured_output` or `serde_json::from_str(&result.stdout)` to determine the verdict — with empty stdout, every script guard hits the "no parseable JSON output" error path and denies (fail-closed). That's safe from a security standpoint but makes script guards functionally unusable until this is fixed. The adapter's tests exercise `parse_structured_output` with synthetic strings, which is why they pass, but the integration path is broken.

## Router's progressive matching and substring risk

The router's `try_script_route` uses three tiers:

1. Exact match: `manifest.id == task_type`
2. Required capabilities list: linear scan against `required_capabilities`
3. Substring: `manifest.id.contains(&task_type)`

Tier 3 is the concern. A `task_type` of `"score"` would match `"script.task-score"` (intentional) but also `"script.scoreboard-render"` or anything else containing "score". The first match wins (`.find()` not `.filter()`), making routing dependent on the order capabilities appear in the registry's internal Vec — which is filesystem traversal order from `load_directory`. If more capabilities are added over time, the substring fallback becomes a source of silent misrouting.

## Scheduler misfire cap at 24 hours

```rust
let max_checks = 1440u32; // 24 hours of minutes
let mut checks_done = 0u32;
while check < now && checks_done < max_checks {
    if cron.matches(&check) { count += 1; }
    check += TimeDelta::try_minutes(1).expect("valid");
    checks_done += 1;
}
```

For a weekly cron task (`0 0 * * 1`), if the system was down for two weeks, `count_missed_triggers` reports at most 1 missed trigger (it only scans 24 hours of minutes). With `MisfirePolicy::RunAll`, the caller expects all missed firings but only gets what fits in 1440 iterations. The cap prevents infinite loops but its scope should match the maximum expected outage window or be documented as a limitation.

## Health monitor failure record growth

`HealthMonitor.failures` is a `Vec<FailureRecord>` pruned only via `check_profile_transition`. Under cascading failures without interleaved health checks, the Vec grows without bound. Adding a capacity check or pruning inside `record_failure` after accumulating more than `2 * threshold_recovery` entries would bound memory under pathological conditions.
