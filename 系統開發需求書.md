# PEARL v2 系統開發需求書

## Constitutional Deterministic Agent Framework

**用途：以 DDP 為實證素材，重新建構一套「確定性優先、Agent 輔助、事件可追蹤、可恢復、可治理」的新框架**

**文件定位：System Requirements Specification / SPEC.md**
**建議版本：v0.1 Draft**
**核心技術方向：Rust Core + SQLite/WAL + Python/PowerShell Script Runtime + Planner–Executor + Event Ledger**

---

# 1. 文件目的

本需求書定義一套新的 Agent Framework，暫稱 **PEARL v2**。

它不是：

* Hermes Agent 的 fork
* DeepSeek Harness 的 wrapper
* Grok Build 的 orchestration layer
* Claude Code 的 Prompt 集合
* DDP 的重新命名

而是：

> **從 DDP 的實際無人值守運作經驗出發，吸收 Hermes、DeepSeek Harness、Grok Build 與既有 PE（Planner–Executor）架構優點，重新建立一套「機械確定性優先、LLM 推理受控、Runtime 可恢復、結果可證明」的 Agent Framework。**

現有 DDP 已具備相當多值得保留的工程資產：YAML 單一真相、PowerShell 協調器、Hooks 機器強制、127+ Skills、448+ Python Tools、19+ Workflows，以及 OODA、自我修復、Runtime Profile、Fallback 等治理機制。 

PEARL v2 的工作不是重新發明這些東西，而是：

> **將 DDP 已經證明有效的做法，從 Prompt、PowerShell、YAML、零散 state files 中抽取成正式 Framework Primitives。**

---

# 2. 最重要的架構修正

上一版有兩個假設需要正式取消。

## 2.1 Grok Build 與 DeepSeek Harness 不列入 Runtime 支援

PEARL v2 **不得假設可以直接掛載：**

```text
Grok Build Runtime
DeepSeek Harness Runtime
```

兩者只作為：

```text
Architecture Reference
Design Pattern Source
Implementation Benchmark
```

而不是 production dependency。

因此 Runtime 支援清單改為：

```text
PEARL Execution Runtime
│
├─ Mechanical Script Runtime
│  ├─ Rust executable
│  ├─ Python CLI
│  ├─ PowerShell
│  └─ Shell
│
├─ Agent CLI Runtime
│  ├─ Claude Code CLI
│  ├─ Codex CLI
│  └─ Cursor CLI
│
├─ LLM API Runtime
│  ├─ OpenAI-compatible
│  ├─ Anthropic-compatible
│  └─ llama.cpp-compatible
│
└─ Native PEARL Worker
```

**Grok Build / DeepSeek Harness 不出現在 Runtime Adapter Contract 中。**

其架構思想仍可借鑑：

* Grok：workflow budget、headless、worktree、hooks、skills compatibility
* DeepSeek：event lifecycle、capability seam、service decomposition
* Hermes：durable queue、reclaim、cron、SQLite、provider fallback

# 3. 框架核心定位

PEARL v2 的正式定位：

> **Deterministic-first Autonomous Execution Framework**

核心公式：

```text
確定性工作
    ↓
機械執行

可精準驗證工作
    ↓
LLM 可參與產生
    ↓
機械驗證

不可完全確定工作
    ↓
LLM 推理
    ↓
Evidence + Policy + Assurance

高風險且不可機械確認
    ↓
禁止自動宣告成功
```

因此新的優先順序不是：

```text
Agent → Tool
```

而是：

```text
Mechanical
    ↓
Workflow
    ↓
LLM-assisted
    ↓
Autonomous Agent
```

**越往下，不確定性越高。**

# 4. 系統開發憲法

以下條文不是 coding guideline。

它們應成為：

> **PEARL Constitution**

Framework、Workflow、Agent、Skill、Tool、Script、PR、ADR 都不得違反。

---

## 憲法第 1 條：確定性優先

> **凡能以確定性程式完成的工作，不得交由 LLM 決定。**

例如：

```text
JSON Schema 驗證
日期運算
檔案存在性
Hash
排序
計數
門檻判斷
timeout
retry
frequency
dependency
configuration consistency
UTF-8/CJK encoding
Git status
測試結果
HTTP status
```

必須由機械程式處理。

不得 Prompt：

> 「請判斷這個 JSON 是否符合 Schema。」

如果 `jsonschema` 可以判斷。

---

# 5. 憲法第 2 條：精準項目必須機械確認

這是新版最重要的規則。

> **凡「已能精準確認」或「業務要求必須精準確認」之項目，必須存在 Machine Verifier。**

分兩種情況。

### A. 已有精確方法

例如：

```text
測試是否通過
JSON 是否合法
Todoist 是否真的完成
檔案是否存在
Git commit 是否存在
資料筆數
API 是否 200
SHA 是否一致
設定是否符合 Schema
```

必須直接以 Script 判斷。

---

### B. 業務要求精準，但目前沒有 Verifier

例如：

```text
「一定不能少任何一筆資料」
「所有引用一定存在」
「不得有重複通知」
```

則任務狀態不得直接進：

```text
SUCCESS
```

而應：

```text
UNVERIFIED
```

直到：

```text
建立 verifier
```

或：

```text
Human Gate
```

完成。

**LLM 自評不能取代 Verifier。**

---

# 6. 憲法第 3 條：LLM 不負責 Infrastructure

Prompt 不得負責：

```text
retry
timeout
fallback
queue
locking
process cleanup
heartbeat
schedule
schema validation
idempotency
dependency
circuit breaker
budget enforcement
```

LLM 只負責：

```text
interpret
classify
plan
reason
research
synthesize
recommend
explain
```

這延續 DDP 已有的「Prompt 薄層、邏輯外抽」方向。現有 DDP 已明確將 timeout、frequency、scoring 等搬至 YAML SoT，而非重複放入 Prompt。

---

# 7. 憲法第 4 條：所有成功都必須可證明

不得只有：

```json
{
  "status": "success"
}
```

至少必須有：

```json
{
  "status": "success",
  "result": {},
  "evidence": [],
  "verification": [],
  "artifacts": [],
  "runtime": {},
  "metrics": {}
}
```

即：

> **Success = Result + Evidence + Verification**

沒有 Evidence：

```text
不得成為 VERIFIED_SUCCESS
```

---

# 8. 憲法第 5 條：Side Effect 必須冪等

所有外部副作用：

```text
send notification
complete Todoist
send email
write DB
write artifact
git commit
publish
delete
```

必須有：

```text
idempotency_key
```

例如：

```text
todoist:complete:task_123:run_456
ntfy:daily_digest:2026-08-15
```

Runtime retry 不得造成重複副作用。

---

# 9. 憲法第 6 條：狀態必須持久化

不能只有：

```text
process memory
```

任何超過單步操作的工作，都必須有：

```text
Task
Run
Attempt
Checkpoint
Event
```

系統重啟後：

```text
能知道發生什麼事
能知道做到哪裡
能知道能否重試
```

---

# 10. 憲法第 7 條：Guard Fail-Closed

必須區分：

### Hook

```text
logging
metrics
notification
telemetry
```

失敗：

```text
可以 fail-open
```

### Guard

```text
secret
security
filesystem boundary
production write
dangerous shell
budget
side effect
```

失敗：

```text
必須 fail-closed
```

現有 DDP 已經有 `pre_bash_guard.py`、`pre_write_guard.py`、CJK 檢查與工具 logging 等「機器強制層」，PEARL 應將此概念提升為 Runtime Primitive。

---

# 11. 憲法第 8 條：LLM 不能自行宣布驗證通過

禁止：

```text
Agent:
"我已檢查，測試應該沒問題。"
```

必須：

```text
Agent
 ↓
Script verifier
 ↓
pytest / cargo test / schema / hash / query
 ↓
PASS
```

---

# 12. 憲法第 9 條：所有 Runtime 都必須可取消

任何 Runtime Adapter 必須提供：

```text
spawn
status
cancel
timeout
cleanup
```

不能可靠取消的 backend：

```text
不得成為正式 Runtime
```

---

# 13. 憲法第 10 條：所有配置只有一個 SoT

現有 DDP 已採：

```text
global YAML
    ↓
per-task override
    ↓
runtime override
```

並明確將 frequency / timeout 等配置視為唯一真相。

PEARL 保留這個原則，但正式化為：

```text
Config Resolution

System
  ↓
Profile
  ↓
Task Type
  ↓
Task
  ↓
Runtime Emergency Override
```

每次 Run 必須記錄：

```text
config_revision
config_hash
```

才能事後重現。

---

# 14. 憲法第 11 條：自主程度必須與可驗證程度成反比

```text
Verification ↑
Autonomy     ↑

Verification ↓
Autonomy     ↓
```

也就是：

> **不是模型越強就給越大權限，而是系統越能驗證，才給越高自主權。**

---

# 15. 憲法第 12 條：架構變更必須經 ADR

Self-Heal 可以：

```text
提出改變
實作候選
測試候選
```

但 architecture-level change 必須：

```text
Finding
 ↓
Proposal
 ↓
ADR
 ↓
Verification
 ↓
Promotion
```

DDP 已有 System Audit → System Insight → ADR → Self-Heal 的 OODA 閉環，應保留並制度化。

# 17. Precision Decision Engine

這是 PEARL v2 新增的核心模組。

每個 Step 執行前必須先分類。

定義四類：

| 等級 | 類型                        | 執行原則                         |
| -- | ------------------------- | ---------------------------- |
| P0 | Deterministic             | 100% Script                  |
| P1 | Generative but Verifiable | LLM 產生 + Script 驗證           |
| P2 | Partially Verifiable      | Script facts + LLM reasoning |
| P3 | Subjective / Exploratory  | Agent + Evidence             |

---

# 18. P0：完全機械化

例如：

```text
計算 task score
解析 YAML
檢查 Schema
判斷時間窗
查 cache age
Git diff
API health
比對 hash
排序
聚合統計
```

禁止 LLM。

例如目前 DDP Todoist scoring：

```text
priority 0.30
due_score 0.25
subtask_health 0.20
...
```

這種明確公式應完全歸 Mechanical Script，不需要 Agent 判斷。現行 DDP 本身已將這些權重放在 `scoring.yaml`。

---

# 19. P1：LLM 產生、機械驗證

例如：

```text
產生程式碼
產生 JSON
產生配置
產生 Markdown frontmatter
修改 Workflow
修改 SQL
```

流程：

```text
LLM
 ↓
candidate
 ↓
Machine Verifier
 ├─ parser
 ├─ schema
 ├─ compiler
 ├─ test
 └─ lint
 ↓
PASS
```

只有 Machine Verifier 通過：

```text
VERIFIED
```

---

# 20. P2：部分可驗證

例如研究報告：

```text
資料是否取得         → Script
來源 URL 是否存在    → Script
日期是否合理         → Script
引用是否重複         → Script
結論是否有意義       → LLM
推薦是否合理         → LLM
```

因此：

```text
Facts → Machine
Interpretation → Agent
```

---

# 21. P3：開放性任務

例如：

```text
創意
策略
架構建議
研究方向
摘要敘事
禪語
```

可用 Agent。

但仍必須：

```text
record sources
record model
record prompt revision
record output
```

不能成為黑箱。

# 22. Exactness Gate

每個 Task Spec 新增：

```yaml
quality:
  exactness_required: true
  deterministic_generation: false
  deterministic_verification: true
```

Runtime 判斷：

```text
exactness_required = true
        +
deterministic_verification = false
            ↓
       BLOCK AUTO-COMPLETE
```

必須：

```text
建立 verifier
        OR
Human Approval
```

# 25. Mechanical Script Contract

所有正式 script 必須具有 manifest：

```yaml
id: verifier.todoist-result
version: 1

kind: verifier
runtime: python

entrypoint:
  module: tools.validate_results
  args:
    - --phase3

input_schema:
  ref: schemas/todoist-result.json

output_schema:
  ref: schemas/verification-result.json

deterministic: true
side_effects: false

timeout_seconds: 60
retry:
  max_attempts: 1
```

# 28. Planner–Executor 架構

PE 保留，但明確限定 Planner 權責。

```text
Intent
 ↓
Planner
 ↓
Typed Execution Plan
 ↓
Plan Compiler
 ↓
Executor
 ↓
Assurance
```

DDP 已在 2026-05-30 將 LangGraph 工作流往純 Python node sequence + PlannerExecutor 演進，因此 PEARL 應延續此方向，而非重新回到 graph framework 綁定。

---

# 29. Planner 不直接執行

Planner 只能產生：

```yaml
steps:
  - id: collect
    capability: script.news.collect

  - id: summarize
    capability: agent.summarize
    depends_on:
      - collect

  - id: verify
    capability: verifier.digest
```

Planner 不可以直接：

```text
run shell
寫檔案
呼叫 API
發通知
```

---

# 30. Plan Compiler

這是重要安全層。

Compiler 必須檢查：

```text
Schema
Capability exists
Dependency DAG
Policy
Budget
Precision classification
Verifier presence
Platform compatibility
Timeout
Idempotency
```

若：

```text
exactness_required=true
```

但沒有 verifier：

```text
CompileError::MissingVerifier
```

---

# 31. Executor

Executor 只執行「已 compile 的 Plan」。

不得：

```text
自行更改 policy
擴張工具
忽略 dependency
自行增加 side effect
```

需要變更：

```text
Executor
 ↓
ReplanRequest
 ↓
Planner
```

# 32. Assurance Engine

每個 Step 可配置：

```yaml
assurance:
  - schema
  - script: verifier.foo
  - test: tests/foo
  - evidence_required
```

Task 完成條件：

```text
Execution finished
      ≠
Task succeeded
```

必須：

```text
Execution
 ↓
Assurance
 ↓
VERIFIED_SUCCESS
```

---

# 33. Durable Work Plane

必須建立正式工作狀態機：

```text
CREATED
   ↓
PLANNING
   ↓
PLANNED
   ↓
READY
   ↓
LEASED
   ↓
RUNNING
   ↓
VERIFYING
   ↓
VERIFIED_SUCCESS
```

異常：

```text
RUNNING
 ├─ RETRY_WAIT
 ├─ BLOCKED
 ├─ FAILED
 ├─ CANCELLED
 └─ DEAD
```

---

# 34. Lease

Worker claim 時：

```text
task_id
worker_id
lease_id
leased_until
last_heartbeat
```

Worker crash：

```text
heartbeat stops
 ↓
lease expires
 ↓
reaper
 ↓
READY
```

避免：

```text
永遠卡 RUNNING
```

---

# 35. Attempt

每次執行：

```text
Run
 ├─ Attempt 1
 ├─ Attempt 2
 └─ Attempt 3
```

每個 Attempt 保存：

```text
runtime
start
end
exit reason
evidence
logs
cost
```

# 36. Process Supervisor

必須為核心元件。

職責：

```text
spawn
```

# 41. Workflow Checkpoint

每個 durable step 完成：

```text
Step
 ↓
Artifact
 ↓
Evidence
 ↓
Commit checkpoint
```

只有 checkpoint committed：

```text
下一步
```

Process crash 後：

```text
Last committed checkpoint
 ↓
Resume
```

不能依賴 LLM 自己「記得上次做到哪」。

# 44. State、Memory、Cache、Artifact、Evidence 必須分離


```text

```


# 51. Fallback

Agent fallback 保留 DDP 成熟經驗。

但：

```text
Claude → Codex
```

不應只看 service failure。

要判斷：

```text
runtime compatible?
task risk?
remaining budget?
required capability?
```

而 Script：

```text
不得 fallback 到 Agent
```

來取代 deterministic correctness。

例如：

```text
JSON verifier crash
```

不能：

```text
請 Claude 幫忙看看 JSON 有沒有錯
```

正確：

```text
Retry verifier
 ↓
alternate deterministic verifier
 ↓
BLOCKED
```

這也是憲法條款。

# 72. 新框架最核心的一句話

如果要把整份需求書濃縮成一句工程原則，就是：

> **能算的不要猜，能驗的不要信，不能驗的不要假裝確定。**

對應：

```text
能算
 ↓
Mechanical Script

能驗
 ↓
Machine Verifier

不能精準驗
 ↓
Agent + Evidence

要求精準但不能驗
 ↓
BLOCK / Human Gate
```

這應成為 PEARL v2 和一般 Agent Framework 最大的差異。

# 73. 最終框架定位

因此新版 PEARL 不再是：

```text
Agent Runtime Framework
```

而更精準地說，是：

> **一個由「系統憲法」約束、以機械確定性為底層、以 Planner–Executor 管理不確定性、以 Agent 補足推理能力、以 Event Ledger 與 Machine Verification 保證可恢復與可證明性的 Autonomous Execution Framework。**

三套參考框架的定位也就變得非常清楚：

```text
Hermes
  → Durable Work / operational patterns

DeepSeek Harness
  → Event / capability architecture reference

Grok Build
  → Workflow / isolation / headless design reference

DDP
  → Production evidence + migration source

PE
  → Planning / execution separation

PEARL v2
  → 自己的 Framework
```

而 **DDP 最終只是 PEARL 的第一個正式 Application**：

```text
PEARL Framework
│
├─ Constitutional Kernel
├─ Mechanical Runtime
├─ Planner–Executor
├─ Durable Work
├─ Assurance
├─ Governance
│
└── DDP Application
    ├─ Daily Digest
    ├─ Todoist Automation
    └─ System Audit / Self-Heal
```
